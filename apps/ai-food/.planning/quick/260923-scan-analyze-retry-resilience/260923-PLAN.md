# Plan: Scan / analyze resilience + Retry fix

**Slug:** `260923-scan-analyze-retry-resilience`  
**Date:** 2026-09-23  
**Goal:** Починить «залипший» анализ / мёртвую «Повторить», снизить порог stale до **20s**, покрыть пайплайн полноценными unit + e2e тестами (медленный/обрыв сети, hang SSE, kill→reopen).

---

## Problem

Пользователь сканирует еду → карточка долго в загрузке → «Анализ не завершился…» + **Повторить**. Клик не меняет UI (запрос может уходить, карточка остаётся в том же состоянии).

### Root causes (код)

1. **`MealCard`:** stale-таймер **не стартует**, если есть `analyzeJobId` (`if (!isAnalyzing || meal.analyzeJobId) return`). Job id приходит почти сразу с SSE → при зависании стрима/poll пользователь **никогда** не видит stale-Retry на той же сессии (или видит лоадер поверх error).
2. **`mealShowsAnalyzeLoader`:** при `analyzeJobId` всегда loader, даже при `status: 'error'` (кроме terminal codes).
3. **`analyzeErrorPatch`:** `ANALYSIS_TIMEOUT` **не** чистит `analyzeJobId` → карточка остаётся «in-flight» для UI.
4. **`useRetryAnalyzeMeal`:** при старте **не** сбрасывает `analyzeJobId` → старый job id держит loader-семантику до `onJobId`.
5. **Stale 45s** слишком долго: бэкенд analyze ~15s + сеть → UX-порог должен быть **20s**.

### Out of scope

- Нативный Detox/Espresso kill APK (нет инфраструктуры) — kill симулируем через `page.reload` + persist diary.
- Снижение серверного `ANALYZE_JOB_DEADLINE_MS` / SSE 120s (отдельное решение; клиентский UX-порог независим).
- Изменение квоты / NO_FOOD UX.

| Risk | Mitigation |
|------|------------|
| Stale Retry на живом job в 15–20s окно (медленная сеть, анализ ещё идёт) | Acceptable: user force-retry; beginMealAnalyze abort + новый job. Backend ~15s → 20s даёт ~5s запас. |

3. Автотесты воспроизводят hang / offline / throttle / reload / Retry→success без ручного APK.
