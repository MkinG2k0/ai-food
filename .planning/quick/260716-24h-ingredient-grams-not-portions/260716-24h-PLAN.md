## Locked decisions (do not reopen)

**D-01 — Types:** Replace `FoodItem.portion: string` with `FoodItem.grams: number` (integer via Math.round / sanitize). Replace `NutritionItem.portion?: string` with `NutritionItem.grams?: number`.

**D-02 — AI prompt:** `SYSTEM_PROMPT` in client `analyzeFoodApi.ts` must ask for grams estimate of the visible amount of each ingredient. Never exemplify piece-count or serving-count portion strings.

**D-03 — UI:** Badge text `"${Math.round(grams)} г"` via `resolveItemGrams` everywhere portion was shown (`FoodItemDisplayCard`, `FoodItemEditPage`). Edit page: number input for grams; persist with `updateMealItem`.

**D-04 — Save mapping:** `useSaveMeal` maps `item.grams ?? 100`; placeholders and empty-items fallback use `grams: 100` (not a portion string).

**D-05 — Legacy:** `resolveItemGrams(item)` accepts `FoodItem & { portion?: string }`: if `grams` is a finite number use rounded max(0,n); else parse leading number from legacy `portion`; else `100`. Display must not crash.

**D-06 — No KBJU scaling:** Editing grams is metadata/display only — do not call `scaleItemsNutrient` or otherwise change calories/protein/carbs/fat when grams change.

**D-07 — Tests:** All portion fixtures → grams; prompt tests assert grams in SYSTEM_PROMPT and that piece/serving unit examples are absent.

**D-08 — Backend:** Skip unless shared-types break backend compile. Prefer client gateway path; type-check must pass.

## Out of scope

KBJU recalculation from grams; capacitorStorage; ProfileGuard; onboarding; unrelated dirty files; new npm dependencies.
