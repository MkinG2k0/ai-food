## Architecture reality (do not invent ResultPage)

- `pages/result/` is an empty stub — **no ResultPage**. Analysis is not a separate route.
- Live flow: `AddFoodSheet` → `useSaveMeal` → diary meal with `status: 'analyzing' | 'ready' | 'error'`.
- Error UI today: `MealCard` shows «Ошибка анализа…» with **no** retry control.
- `useAnalyzeFood` exists but is **unused** by pages — do not wire retry through that hook; keep the diary-status model.
- Photo is persisted via `saveMealImage` → `meal.imageUri`; text path keeps description on `meal.name` while pending/error.

## Locked decisions (honor exactly)

- **D-01 Surface:** Primary retry CTA on `MealCard` when `meal.status === 'error'` (home/diary list). Do not recreate ResultPage.
- **D-02 Label:** Button text exactly «Повторить» (Russian).
- **D-03 Behavior:** Retry re-analyzes the **same** meal id — set `status: 'analyzing'`, call `analyzeFoodApi`, then apply the same success/error `updateMeal` outcomes as `useSaveMeal`.
- **D-04 Inputs:** If `meal.imageUri` present → load bytes and build a `File` for `analyzeFoodApi`. Else if non-empty `meal.name` (and not the analyzing placeholder) → `analyzeFoodApi({ description: meal.name })`. If neither usable → leave status `error` (no silent no-op success).
- **D-05 Click isolation:** «Повторить» must `stopPropagation` / `preventDefault` so the card does not navigate to `/meal/:id` when retrying.

## Discretion

- Optional thin helper `loadMealImageAsFile(imageUri)` in `shared/lib/mealImage.ts` (mirror refine’s Filesystem read, but return `File` for analyze). Export via `shared/lib` barrel.
