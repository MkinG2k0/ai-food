<interface>
Contracts this plan creates. Implement these names and shapes; do not invent parallel APIs.

Prisma FriendRequest (D-02, D-03)
- enum FriendRequestStatus: pending | accepted | declined
- model FriendRequest: id cuid, fromUserId, toUserId, status default pending, createdAt, updatedAt
- @@unique([fromUserId, toUserId]); @@index([toUserId, status]); @@index([fromUserId, status])
- User relations: sentFriendRequests, receivedFriendRequests

Settings extension (D-01)
- settingsPayloadSchema gains sharePhotosToFriends: z.boolean() default true on parse when missing
- useSettingsStore: sharePhotosToFriends boolean default true, setter bumps clientUpdatedAt
- Persist version bump + migrate default true for existing rows

resolveFriendTarget(prisma, rawQuery): Promise&lt;User row id, username, firstName&gt;
- Trim input; strip leading @; lowercase username branch
- If /^\d+$/ → User.findUnique by telegramId exact match
- Else → User.findFirst where lower(username) equals normalized query (case-insensitive)
- null → USER_NOT_FOUND

POST /user/friends/request body { query: string } (X-User-Token) (D-02, D-04)
- 401 without token
- 400 SELF_REQUEST when target.id === caller
- 400 ALREADY_FRIENDS when accepted row exists either direction
- 400 REQUEST_PENDING when pending row exists either direction (reuse same row if caller re-sends)
- 201 { requestId, status: 'pending' }
- On create (new pending): sendMessage(Number(toUser.telegramId), Russian text: «{displayName} хочет добавить вас в друзья. Откройте AI Food → Друзья.») — fire-and-forget; log ApiError, do not fail HTTP if Telegram down (D-03)

GET /user/friends (X-User-Token) (D-05, D-06)
- 200 { friends: FriendSummary[] } sorted by streak DESC
- FriendSummary: userId, displayName, username, streak (clientStreak.currentLength or 0), photoUrl?

GET /user/friends/requests (X-User-Token) (D-03)
- 200 { incoming: FriendRequestItem[], outgoing: FriendRequestItem[] }
- FriendRequestItem: requestId, userId, displayName, username, createdAt

POST /user/friends/requests/:id/accept | /decline (X-User-Token) (D-03)
- Only recipient (toUserId) may accept/decline pending
- 404 when not found or not recipient
- accept → status accepted; decline → status declined
- No Telegram message on accept/decline (D-03)

GET /user/friends/:userId/profile (X-User-Token) (D-01, D-06)
- 403 FRIENDS_ONLY when no accepted FriendRequest between caller and :userId
- 200 FriendProfile: userId, displayName, streak, goalKg, weightKg (latest non-deleted WeightEntry by date desc), targets from nutritionProfile.targets, sharePhotosToFriends from friend clientSettings (default true), meals: last 7 calendar days UTC of ready meals where deletedAt null — fields: id, timestamp, name, totalCalories, protein/fat/carbs summed from items JSON; never return imageUri/imageUris

friendsApi.ts mirrors fetchReferral: gatewayBase + getQuotaHeaders + parseError
useFriendsList, useFriendRequests, useFriendProfile — React Query hooks with staleTime ~30s
</interface>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → /user/friends/* | JWT identifies caller; only friendship grants profile access |
| Gateway → Telegram API | Bot token sends DM to recipient telegramId on new request |
| Friend profile → Meal rows | Cross-user read scoped to accepted friends; no photo blobs |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-2so-01 | Spoofing | /user/friends/* | high | mitigate | verifyUserToken on every route; userId from JWT only (D-04) |
| T-2so-02 | Information Disclosure | GET /:userId/profile | high | mitigate | assertFriendship before any Meal/User read; strip imageUri fields (D-01, D-06) |
| T-2so-03 | Elevation of Privilege | accept/decline | high | mitigate | Only toUserId may change request status |
| T-2so-04 | Information Disclosure | sharePhotosToFriends | medium | mitigate | Friend sees flag only via profile endpoint; meals never include blobs (D-01) |
| T-2so-05 | Denial of Service | POST /request | medium | accept | Existing unique constraint prevents duplicate rows; no extra rate limit in quick task |
| T-2so-SC | Tampering | sendMessage | medium | mitigate | Use existing telegramBotApi; Telegram failure must not block request creation (D-03) |
</threat_model>
